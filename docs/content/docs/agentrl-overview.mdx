# AgentRL

AgentRL is the orchestration loop of Bricks ADK for coding tasks that must be verified. You give it a task and a **verifier**, a command or a check that decides whether the work is done. AgentRL first looks for a registered tool that already solves a similar task. Then it runs a general coding agent. If that run fails the verifier, it traces the failure, asks a planner agent for fixes, tries those fixes in isolated working copies, promotes the one that passes, and registers it as a new tool for later tasks.

<Callout type="warn">
**AgentRL is opt-in and not used by the `bricks` command-line tool or the desktop app.** It is a library feature, enabled with `features = ["agentrl"]` on the `bricks` facade. Its production runner has no approval step. Read [the safety notes](#safety) before running it on a project.
</Callout>

## The loop

```text
  task ──▶ registry.search(task) ──▶ general agent (+ matching registered tools)
                                            │
                       verifier passes? ────┴──── yes ──▶ solved (Directly / ByCachedTool)
                                            │
                                            no
                                            ▼
                     ExecutionGraph.failure_trace()  (ordered, secret-scrubbed)
                                            │
                                            ▼
                     planner agent ──▶ up to num_proposals proposals
                                            │
                     each proposal runs in its own working copy, then is verified
                                            │
                     first passing proposal (in proposal order) ──▶ promote to the workdir
                                            │
                     register it as a tool, record the problem in memory ──▶ solved (ByNewTool)
```

The parts:

- **ExecutionGraph**: a graph of agent runs, turns and tool calls, built from the agent's events by a `GraphReporter`. On failure it yields a `FailureTrace` with the failing tool calls and their excerpts.
- **General agent and planner**: ordinary `Agent`s with different prompts and tool sets.
- **Proposal runs**: each proposal runs a coding agent in a temporary copy of the working directory.
- **ToolRegistry**: a persisted list of solutions, searched by keyword. A solution is a `SolutionSpec` (system prompt, goal template, allowed tools).
- **Verifier**: decides success for the general agent and for every proposal, with the same check.

## What the production runner does

`CerseiRunner` is the built-in `AgentRlRunner`. Its behaviour, from the code:

| Step | What happens |
|---|---|
| General run | The agent runs **in the working directory itself**, with the coding tools (`bricks::tools::coding()`), `registry_search`, and one `DynamicTool` per registry entry found by the search. Its permission policy allows everything (`AllowAll`). |
| Verification | The verifier runs in the working directory after the general run. A failure adds a synthetic node to the graph so the planner has something to act on. |
| Planning | A planner agent returns a JSON list of `{angle, goal}`. If that cannot be parsed, built-in angles are used. |
| Proposal runs | Each proposal copies the working directory to a temporary directory, runs a coding agent there with the same verifier, and reports whether it passed. |
| Promotion | The winning copy is copied back over the working directory. |

<Callout type="info">
Proposals are isolated by copying, not by a `bricks-vms` sandbox. To run proposals in containers, implement `AgentRlRunner` yourself and use sandboxes there; see the [cookbook](/docs/agentrl-cookbook#5-a-custom-runner).
</Callout>

## Safety

- **The general agent writes to your working directory with no approval step.** `CerseiRunner` uses `AllowAll`. Point it at a copy of the project, or at a directory you are willing to change.
- **The verifier is your guarantee.** It must check real behaviour and must not depend on files the agent can write. See [the verifier notes](/docs/agentrl-api#verifier).
- **Secrets are scrubbed** from the failure trace, registry entries and memory hints (API-key shapes and values of secret-looking environment variables). The scrubbing is pattern-based; it does not replace keeping secrets out of the project.

## A short example

```rust
use bricks::agentrl::{CerseiRunner, CommandVerifier, Orchestrator, ToolRegistry, Verifier};
use bricks::provider::Provider;
use bricks::ProviderRegistry;
use std::sync::Arc;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    // Registered solutions persist in this directory.
    let registry = ToolRegistry::open(dirs::home_dir().unwrap().join(".cersei/agentrl"))?;

    // An independent check: the agent cannot change what this command tests.
    let verifier: Arc<dyn Verifier> =
        Arc::new(CommandVerifier::new("python3 gcd.py 48 36 | grep -qx 12"));

    // provider_id/model_id, as defined in ~/.bricks/providers.toml.
    let model = ProviderRegistry::load(None)?.resolve("my_provider/my-model")?;
    let selection = model.selection();
    let provider_factory = Arc::new(move || {
        model.build_provider().expect("provider builds").into_boxed() as Box<dyn Provider>
    });

    let runner = Arc::new(
        CerseiRunner::new(provider_factory, "./work", registry.clone(), verifier)
            .with_model(&selection),
    );

    let outcome = Orchestrator::new(runner, registry)
        .solve("Create gcd.py: takes two ints, prints their GCD via the Euclidean algorithm.")
        .await?;

    println!("solved={} how={:?}", outcome.solved, outcome.how);
    Ok(())
}
```

`with_model` sets the model the runner gives to every agent it builds. Pass the same `provider_id/model_id` string the provider was resolved from.

## Outcomes

`Orchestrator::solve` returns `SolveOutcome { solved, how, … }`, where `how` is one of:

| `Solved` | Meaning |
|---|---|
| `Directly` | The general agent passed the verifier, with no registered tool used. |
| `ByCachedTool(id)` | The general agent passed, and it used a registered tool that the search found. |
| `ByNewTool(id)` | The general agent failed, a proposal passed, and the proposal was registered as tool `id`. |

If no proposal passes within `max_rl_rounds` rounds, `solved` is `false` and `how` is `None`.

<Callout type="info">
This repository does not keep a recorded result of a live AgentRL run, so no success rate is claimed here. The opt-in live test in `crates/bricks-agentrl/tests/live_agentrl.rs` runs the loop against a model you name; see the [cookbook](/docs/agentrl-cookbook#2-force-the-recovery-loop-and-register-a-tool).
</Callout>

## Install

```toml
[dependencies]
bricks = { version = "0.6", features = ["agentrl"] }
tokio = { version = "1", features = ["full"] }
anyhow = "1"
```

The feature enables `bricks::agentrl` (the loop) and `bricks::agentlang` (the AgentTemplate language), and turns on the `vms` feature.
