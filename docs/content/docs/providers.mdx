# Providers

Which providers and models Bricks can use is decided by **one file**:
`~/.bricks/providers.toml`, or any `.toml` or `.json` path you pass. Adding a
provider, or a model that speaks one of the three supported wire protocols, is a
configuration change: no code, no recompilation. Environment variables serve one
purpose only: resolving the secrets that the file names.

The authoritative reference is `docs/providers.md` in the repository. A
secret-free annotated example is `docs/providers.example.toml`; a unit test
loads it, so it cannot drift from the schema.

<Callout type="info">
Models are never inferred from a name. Every model is selected as
`provider_id/model_id`, and the provider is never guessed from the model.
</Callout>

## Quick start

```toml
# ~/.bricks/providers.toml
schema_version = 1

[[providers]]
id = "my-provider"
name = "My provider"
endpoint = "https://api.example.com/v1"
protocol = "chat_completions"
auth = "bearer"
api_key_env = "MY_PROVIDER_API_KEY"   # the name of a variable, never the key

[[providers.models]]
id = "my-model"
name = "My model"
api_model = "vendor-model-id"          # sent to the server exactly as written
streaming = true

[providers.models.limits]
max_input_tokens = 96000
max_output_tokens = 8000
```

The Rust side loads one configured model and gives it to the agent:

```rust
use bricks::prelude::*;

let provider = bricks::provider_from_config(None, "my-provider/my-model")?;
// Some(path) instead of None reads that file, which replaces the default one.

let agent = Agent::builder()
    .provider(provider)
    .tools(bricks::tools::coding())
    .build()?;
```

The command line selects the same way:

```bash
bricks --model my-provider/my-model
bricks --providers ./providers.toml --model my-provider/my-model
```

## The file

* **Location.** `~/.bricks/providers.toml`, or the path given explicitly. An
  explicit path **replaces** the default; the two are never merged. A missing
  file is an error: there is no built-in catalogue.
* **Format.** TOML or JSON, with the same structures, defaults and validation.
  Any other extension is rejected.
* **`schema_version = 1`** is required.
* **No cap** on the number of providers or of models per provider.
* **Selection** is `provider_id/model_id`, split at the first `/` (model ids may
  contain `/`). Provider ids are unique; model ids are unique within a provider.
* **Errors are located and secret-free**, for example
  `providers.toml: provider "custom", model "flash", field limits.max_input_tokens: must be greater than 0`.
  A type error never echoes the offending value.

## Editing from the desktop app

The settings page « Modèles » of the desktop app edits `providers.toml` in place.
The file must already exist: the app does not create it.

* **Adding.** « Ajouter un fournisseur » writes a `[[providers]]` table, and the « + »
  of a provider writes a `[[providers.models]]` table with its `[limits]`.
  Identifiers use letters, digits, `.`, `_` and `-`, start with a letter or a digit,
  and are unique.
* **Required fields.** A provider needs `name`, `endpoint`, `protocol` and `auth`, and
  an `api_key_env` unless `auth = "none"`. A model needs `name`, `api_model`,
  `max_input_tokens`, `max_output_tokens` and the three prices (see *Prices and usage*).
* **Editing.** Only the tables concerned change; comments, order and the other tables
  are kept byte for byte. The whole file is validated before writing, and a refused
  change writes nothing. A provider or model written as an inline table cannot be
  edited from the app.
* **Conflicts.** If the file changed since the page was read, nothing is overwritten:
  the values are reloaded for checking.

## Provider and model fields

| Field | Required | Meaning |
|---|---|---|
| `id` | yes | Stable identifier: non-empty, no whitespace, no `/`. |
| `name` | yes | Display name. |
| `endpoint` | yes | Base URL, possibly with a version (`/v1`), a gateway prefix or a query string. `http` or `https`, no embedded credentials. |
| `protocol` | yes | Default protocol of the provider's models: `chat_completions`, `responses` or `anthropic_messages`. |
| `auth` | yes | `bearer`, `api_key_header` or `none` (local servers). |
| `auth_header` | no | Header that carries the key with `api_key_header` (default `x-api-key`). |
| `api_key_env` or `api_key` | one of | The name of the environment variable that holds the key (recommended), or an inline key for a purely local setup. Neither is allowed with `auth = "none"`. |
| `path` | no | Replaces the protocol's relative path for models that use the provider's default protocol. |
| `headers` | no | Extra static request headers. Their values are secrets and are never printed. |
| `compat` | no | Protocol quirks (see below). |
| `models` | no | The provider's models. |

A model takes `id` (local, unique in the provider), `name`, `api_model` (the
identifier the server receives), and optionally its own `protocol`, `endpoint`,
`path`, `auth`, `headers` and `compat`. It declares its capabilities and limits:

| Model field | Meaning |
|---|---|
| `input_modalities`, `output_modalities` | Subsets of `text`, `image`, `audio`, `video`, `document`. Default `["text"]`. |
| `document_mime_types` | Accepted MIME types when `document` is an input. |
| `streaming` | **Default `false`**: an undeclared streaming is a blocking request. |
| `limits` | `max_input_tokens`, the input usable with the maximum output reserved, and `max_output_tokens`. |
| `pricing` | USD per million tokens (see *Prices and usage*). |
| `reasoning` | Reasoning profiles (see *Reasoning profiles*). |
| `parameters` | Request parameters sent with every request. |
| `remove_parameters` | JSON Pointers removed from the request before `parameters` are merged. |
| `token_counting` | Opt-in pre-flight counting endpoint (see *Limits and counting*). |

Limits are declarative. They never change the server's own limits: Bricks uses
them to cap `max_tokens` and to budget the prompt. Local token counts are
estimates; only a usage reported by the server, or a configured counting
endpoint, measures tokens.

## Protocols and authentication

A protocol defines the request, the response and the streaming format.

| Protocol | Relative path | Conventional auth | Required headers |
|---|---|---|---|
| `chat_completions` | `chat/completions` | `bearer` | none |
| `responses` | `responses` | `bearer` | none |
| `anthropic_messages` | `messages` | `api_key_header` (`x-api-key`) | `anthropic-version: 2023-06-01` |

The request URL is the `endpoint` plus the relative path. A version segment at
the end of the endpoint is not repeated, and an absolute `path` URL is used as
it is. A model can override the protocol; it then takes that protocol's path,
authentication style and headers, and explicit `headers` override by name.

`compat` adjusts the protocol for servers that differ:

| `compat` field | Default | Meaning |
|---|---|---|
| `max_tokens_field` | `max_tokens` | `chat_completions`: name of the output-limit field, for example `max_completion_tokens`. |
| `reasoning_field` | none | `chat_completions`: also send reasoning back under this field on assistant turns with tool calls. |
| `stream_usage` | `true` | `chat_completions`: ask for usage in the stream. |
| `prompt_cache_markers` | `true` | `anthropic_messages`: place cache breakpoints on the stable prefix. |

Keys are held in a type whose `Debug` output is redacted, and they are removed
from every error Bricks produces, including an API error body that echoes them.

## Reasoning profiles

A reasoning profile is an **id**, a **label** and **parameters**. Bricks keeps
no list of levels: the ids are yours, and the server decides whether a value is
valid.

```toml
[providers.models.reasoning]
default = "approfondi"

[[providers.models.reasoning.profiles]]
id = "approfondi"
label = "Approfondi"
parameters = { reasoning = { effort = "high" } }
remove = ["/temperature"]
```

* The id is never sent under its local name: only `parameters` reach the server.
* `profiles = []` exposes no choice for that model.
* A profile is selected with `Agent::builder().reasoning_profile(id)`, with a
  per-request option, or with `provider().reasoning_profile(id)`. Without a
  choice, the model's `default` applies. An unknown id is an error that lists
  the available ids; it is never replaced silently.
* Protected fields (model, messages, system prompt, tools, tool choice,
  streaming control) cannot be set or removed by `parameters`.

## Request identity

A configured provider reports what each request is sent as, through
`Provider::request_identity`: the model name in the request body (`api_model`)
and the reasoning profile applied with the request's options, resolved the same
way as the body. The agent's system prompt states both in its model block, for
each request. An unknown profile id is refused, so nothing is sent, and the
reported profile is then empty. A custom provider that does not override the
method reports nothing, and its prompt states only the Bricks selection. The
server may still run another model behind an alias.

## Capabilities

The capabilities of a request are the ones the model declares **and** the
adapter can transport. A request that needs anything else fails with
`Unsupported`, naming the model and the block, before anything is sent. No
attachment is dropped or converted silently.

| Input | `chat_completions` | `responses` | `anthropic_messages` |
|---|---|---|---|
| text | yes | yes | yes |
| image | data, URL | data, URL, file id | data, URL, file id |
| audio | data (`wav`, `mp3`) | no | no |
| video | no | no | no |
| document | data, file id | data, URL, file id | data (`application/pdf`, `text/plain`), URL, file id |
| media inside a tool result | no | no | image, document |

Model-native output is text only. Tool calls are carried by every adapter. An image a tool returns is carried by the adapter as the table allows, otherwise next to the results or not at all: see [Images returned by tools](/docs/multimodal#images-returned-by-tools).

In the desktop form, *Document* offers the accepted types, with the presets PDF
(`application/pdf`) and any file (`*/*`); at least one type, written `type/subtype`,
is required. Unchecking *Document* removes `document_mime_types`.

## Limits and counting

A request is checked against the prompt budget, `max_input_tokens`, before it
is sent; the output is a separate limit. A server counting endpoint is used only when the model
configures it:

```toml
[providers.models.token_counting]   # opt-in
# path = "messages/count_tokens"    # default: the protocol's documented route
```

It is accepted for `anthropic_messages` and `responses`, which document a
counting route, and refused at load time for `chat_completions`.

## Retry-After budget

The runner retries a retryable error up to five times, waiting the local backoff
(1, 2, 4, 8, 16 s, with jitter) or the server's `Retry-After` when that is
longer. A `Retry-After` longer than `[agent] retry_after_max_wait_ms` (default
`60000`; `0` never waits for one) is not waited for: no retry is sent, and the
run fails at once with a message that names that key.

This budget belongs to the agent. It is not `[web.search] max_retry_wait_ms`,
which bounds only the single rate-limit wait of a web-search provider.

## Prices and usage

* Prices are exact decimals in **USD per 1,000,000 tokens**: `input` (uncached),
  `output`, `cache_read`, and optionally `cache_write`. Named alternative tariffs
  live under `pricing.variants.<name>`, and each one is complete.
* An absent price means **unknown, never free**. A cost is estimated only for the
  categories whose counter and price are both known; otherwise the estimate says
  it is partial and lists what it could not price. With no known price there is
  no estimate at all.
* The desktop form makes `input`, `output` and `cache_read` mandatory, in USD per
  million tokens (`0` allowed), and writes `currency = "USD"` and
  `per_tokens = 1000000` with them. `cache_write`, `cache_write_variants` and
  `variants` are kept as written. The settings page banner « Compléter les coûts
  manquants à 0 » writes `0` for every missing one. The engine is unchanged: a missing
  price is unknown, not free, and a hand-written file may omit any of the three.
* `input_tokens` is always the uncached prompt; cache reads and writes are
  counted apart. `output_tokens` includes reasoning tokens.
* No price list or catalogue is ever downloaded.

## Verification status

The adapters are tested against scripted servers, with no paid call: endpoint
assembly, the three request formats, streamed and non-streaming responses,
errors, reasoning merge and protected fields, refused modalities, limits and
costs.

They are **not** verified against the real vendor APIs, with their quirks and
rate limits. Run your own configuration against your own account before relying
on it.

## Migrating from the Cersei-era providers

The old provider clients (`Anthropic`, `OpenAi`, `Gemini`, their `from_env`
constructors, `Auth`, `from_model_string`, the `--model` aliases and the implicit
`*_API_KEY` and `*_BASE_URL` variables) are removed. The migration table, with
the new calls, is in [Migration to Bricks ADK](/docs/migration).
