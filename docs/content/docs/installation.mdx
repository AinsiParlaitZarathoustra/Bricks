## Requirements

- A recent stable Rust toolchain: edition 2024 and 1.88 or later (the code uses let chains).
- A C++17 compiler. The vector index (USearch) is compiled with the engine, and `bricks-tools` depends on it.
- For Bricks Desktop: Node.js with npm, and the Tauri prerequisites for your platform.
- A model: a hosted API key, or a local server that speaks one of the supported protocols.

The last development builds were made on macOS (arm64). Linux and Windows have not been validated yet.

## Get the source

Bricks is built from a checkout of its repository. Bricks ADK is not published on crates.io under the name `bricks`, which another project uses, so depend on the crates by path or by Git, as described below.

## The `bricks` command

From a checkout:

```bash
cargo install --path crates/bricks-cli
bricks --version
```

This installs the `bricks` binary. Run `bricks` with no argument to see its help. The configuration it reads and its options are described in `docs/cli.md` in the repository.

## Bricks Desktop

From a checkout, in the desktop application's folder:

```bash
cd apps/bricks-desktop
npm ci
npm run tauri dev
```

`npm ci` installs the locked versions from `package-lock.json`. `npm run tauri dev` starts the application, which runs the Vite development server first.

## Bricks ADK in a Rust project

Add the facade crate, `bricks`, with the Tokio runtime and `anyhow` for the examples.

From a checkout, by path:

```toml
[dependencies]
bricks = { path = "/path/to/bricks/crates/bricks" }
tokio = { version = "1", features = ["full"] }
anyhow = "1"
```

From the Git repository, with the revision you want to build against:

```toml
[dependencies]
bricks = { git = "https://github.com/AinsiParlaitZarathoustra/Bricks", rev = "<revision>" }
tokio = { version = "1", features = ["full"] }
anyhow = "1"
```

Replace `<revision>` with a commit hash, a tag or a branch name of your choice. The repository URL is the `repository` field of the workspace `Cargo.toml`.

### Optional features of the facade

The `bricks` crate has these features:

| Feature | Default | Adds |
|---|---|---|
| `vms` | yes | `bricks::vms`: sandbox and VM isolation (`bricks-vms`) |
| `agentlang` | no | `bricks::agentlang`: the AgentTemplate language |
| `agentrl` | no | `bricks::agentrl`: self-evolving orchestration; enables `agentlang` and `vms` |
| `workflows` | no | `bricks::workflows`: the workflow engine |

Enable one in the dependency, for example `bricks = { path = "…", features = ["workflows"] }`.

### Individual crates

You can depend on single crates instead of the facade. Each crate is named `bricks-*` and is in the workspace under `crates/`. The [crate map](/docs/crate-map) lists them with their roles.

## Providers and keys

No environment variable is read implicitly. Each provider entry in `~/.bricks/providers.toml` names the variable that holds its key, with `api_key_env`. The [quick start](/docs/quick-start) shows a complete file. An example file with every section, annotated, is `docs/providers.example.toml` in the repository.

Bricks keeps its files in `~/.bricks`. Set `BRICKS_HOME` to use another folder, and pass `--providers <file>` to the `bricks` command to read another providers file.

## Verify

```bash
cargo test --workspace --locked
```

The tests use scripted models and local test servers. Live API tests are opt-in (`#[ignore]`).
