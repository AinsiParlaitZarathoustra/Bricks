# bricks-vms Cookbook

Recipes for code you write yourself. The examples assume the default `vms` feature of the `bricks` facade and, where a recipe says so, a running Docker daemon. Pair them with the [VMs API](/docs/vms-api) reference. The `bricks` command-line tool does not create sandboxes, so none of these recipes applies to it as shipped.

## Recipe 1: Route an agent's Bash through a sandbox

Every `Bash` call of the agent runs in the sandbox when its handle is in the tool context. The tool list does not change.

```rust
use bricks::prelude::*;
use bricks::tools::Extensions;
use bricks::vms::prelude::*;
use std::sync::Arc;

async fn run() -> std::result::Result<(), Box<dyn std::error::Error>> {
let runtime = LocalProcessRuntime::new()?;
let sandbox: Arc<dyn Sandbox> = runtime
    .create(SandboxOpts::image("cersei/sandbox-base:latest"))
    .await?;

let extensions = Extensions::default();
extensions.insert::<Arc<dyn Sandbox>>(sandbox.clone());

let agent = Agent::builder()
    .provider(bricks::provider_from_config(None, "my-provider/my-model")?)
    .tools(bricks::tools::coding())
    .extensions(extensions)
    .build()?;

let out = agent.run("ls -la /work").await?;
println!("{}", out.text());
Ok(())
}
```

<Callout type="info">
Without a `Sandbox` in the extensions, `Bash` runs on the host as before. Enabling the `vms` feature therefore changes nothing for code that does not insert a sandbox. Only `Bash` is routed: `Read`, `Write` and `Edit` still act on the host.
</Callout>

## Recipe 2: Share a directory between two Docker sandboxes

Two sandboxes mount the same host directory. This is a **Docker** recipe: the Docker backend passes `volume_id` as the host side of `-v` without looking it up in the registry, so `volume_id` must be the host path. The local backend does not mount volumes at all.

```rust
use bricks::vms::prelude::*;
use bricks::vms::VolumeRegistry;

async fn run() -> bricks::vms::Result<()> {
let runtime = DockerRuntime::new()?;
let shared = VolumeRegistry::default_user()?.create(Some("recipe-2".into()))?;

let mount = VolumeMount {
    volume_id: VolumeId(shared.host_path.display().to_string()),
    mount_path: "/shared".into(),
    read_only: false,
};

let a = runtime
    .create(SandboxOpts::image("cersei/sandbox-base:latest").with_volume(mount.clone()))
    .await?;
let b = runtime
    .create(SandboxOpts::image("cersei/sandbox-base:latest").with_volume(mount))
    .await?;

a.commands().run(RunRequest::new("echo from-a > /shared/note.txt")).await?;
let out = b.commands().run(RunRequest::new("cat /shared/note.txt")).await?;
assert_eq!(out.stdout.trim(), "from-a");

a.kill().await?;
b.kill().await?;
Ok(())
}
```

<Callout type="warn">
Passing a registry id (a generated `VolumeId`) instead of the host path makes Docker treat it as a named volume, not as the registry directory. The registry does not translate ids into paths for the backend today.
</Callout>

## Recipe 3: Coordinate two sandboxes through the Mailbox

A coordinator subscribes to a topic, and two sandboxes publish results to it. The subscription must exist before the publish: the mailbox does not keep messages for late subscribers.

```rust
use bricks::vms::prelude::*;
use serde_json::json;

async fn run() -> bricks::vms::Result<()> {
let runtime = LocalProcessRuntime::new()?;
let mailbox = runtime.mailbox();           // the broker shared by this runtime's sandboxes

let worker_a = runtime.create(SandboxOpts::default()).await?;
let worker_b = runtime.create(SandboxOpts::default()).await?;

let mut sub = mailbox.subscribe("workers/results");

mailbox.publish("workers/results", worker_a.id().clone(), json!({ "status": "ok", "tests_passed": 42 }))?;
mailbox.publish("workers/results", worker_b.id().clone(), json!({ "status": "ok", "tests_passed": 17 }))?;

for _ in 0..2 {
    let env = sub.recv().await?;
    println!("from {}: {}", env.from, env.payload);
}

worker_a.kill().await?;
worker_b.kill().await?;
Ok(())
}
```

Inside an agent loop the same exchange uses the `SendVmMessage` and `RecvVmMessage` tools; see Recipe 5.

## Recipe 4: A counter updated by compare-and-swap

Several workers increment one counter without losing updates. Each worker reads the version, then writes only if the version has not changed.

```rust
use bricks::vms::prelude::*;

fn run() -> bricks::vms::Result<()> {
let kv = KvStore::open("counter.json")?;   // a real path: the crate does not expand `~`
kv.set("counter", b"0".to_vec())?;

fn bump(kv: &KvStore) -> bricks::vms::Result<u64> {
    loop {
        let current = kv.get("counter");
        let (value, version) = match &current {
            Some(e) => (
                std::str::from_utf8(&e.value).unwrap().parse::<u64>().unwrap(),
                Some(e.version),
            ),
            None => (0, None),
        };
        if let Some(new) = kv.cas("counter", version, (value + 1).to_string().into_bytes())? {
            return Ok(new.version);
        }
        // Another writer changed the version first: read again and retry.
    }
}

let _ = bump(&kv)?;
Ok(())
}
```

From an agent, `SharedStateSet` with `expected_version` does the same check. A failed check returns the tool error `cas failed: version mismatch`, and the agent can read the key again and retry.

## Recipe 5: Two agents hand off work through the mailbox tools

A scout agent and a worker agent each get their own sandbox, plus the shared mailbox and key/value store in their extensions. The vm tools are added to each tool list explicitly, because they are not registered by default.

```rust
use bricks::prelude::*;
use bricks::tools::{Extensions, vm_tools};
use bricks::vms::prelude::*;
use std::sync::Arc;

async fn run() -> std::result::Result<(), Box<dyn std::error::Error>> {
let runtime = Arc::new(DockerRuntime::new()?);
let scout = runtime.create(SandboxOpts::default()).await?;
let worker = runtime.create(SandboxOpts::default()).await?;

let scout_ext = Extensions::default();
scout_ext.insert::<Arc<dyn Sandbox>>(scout.clone());
scout_ext.insert::<Mailbox>(runtime.mailbox());
scout_ext.insert::<KvStore>(runtime.kv());

let worker_ext = Extensions::default();
worker_ext.insert::<Arc<dyn Sandbox>>(worker.clone());
worker_ext.insert::<Mailbox>(runtime.mailbox());
worker_ext.insert::<KvStore>(runtime.kv());

let mut scout_tools = bricks::tools::coding();
scout_tools.extend(vm_tools::all_vm_tools());
let mut worker_tools = bricks::tools::coding();
worker_tools.extend(vm_tools::all_vm_tools());

let scout_agent = Agent::builder()
    .provider(bricks::provider_from_config(None, "my-provider/my-model")?)
    .tools(scout_tools)
    .extensions(scout_ext)
    .build()?;
let worker_agent = Agent::builder()
    .provider(bricks::provider_from_config(None, "my-provider/my-model")?)
    .tools(worker_tools)
    .extensions(worker_ext)
    .build()?;

// Prompt the scout to call SendVmMessage on topic "plans/v1", and the worker to call
// RecvVmMessage on the same topic with timeout_ms set. Start the worker first: a
// message published before RecvVmMessage has subscribed is not delivered.
let _ = (scout_agent, worker_agent);
Ok(())
}
```

`all_vm_tools()` returns the five tools: `SendVmMessage` and `SharedStateSet` and `SandboxSnapshot` (permission `Write`), and `RecvVmMessage` and `SharedStateGet` (permission `ReadOnly`). The permission policy of the agent applies to them as to any tool. Note that a subscription is created by the first `RecvVmMessage` call on that topic.

## Recipe 6: Snapshot before a risky step, restore on failure

Take a checkpoint, try a migration, and if it fails, restore the checkpoint and run a safer script.

```rust
use bricks::vms::prelude::*;

async fn run() -> bricks::vms::Result<()> {
let runtime = DockerRuntime::new()?;
let sb = runtime.create(SandboxOpts::default()).await?;

sb.commands().run(RunRequest::new("git clone https://example.com/repo /work/repo")).await?;
let checkpoint = sb.snapshot().await?;

let attempt = sb
    .commands()
    .run(RunRequest::new("cd /work/repo && ./scripts/migrate.sh"))
    .await?;

if attempt.exit_code != 0 {
    sb.kill().await?;
    let restored = runtime.restore(&checkpoint).await?;
    restored
        .commands()
        .run(RunRequest::new("cd /work/repo && ./scripts/migrate-safe.sh"))
        .await?;
}
Ok(())
}
```

Snapshot manifests are JSON files in `~/.cersei/vms/snapshots/`, so a checkpoint survives a restart of the host process. For Docker, the file system is the image `cersei-snapshot:<id>`.

<Callout type="warn">
`restore()` also writes the snapshot's key/value state back into the runtime's `KvStore`, which every sandbox of that runtime shares. Do not restore a checkpoint while other sandboxes are still using the store.
</Callout>

## Recipe 7: Build the Docker reference image

The reference image bakes in the `cersei-envd` binary. Build the binary for Linux, then build the image from the repository root so that the binary path is inside the build context.

```bash
# 1. Build the envd daemon as a static Linux binary (needs the musl target installed).
cargo build --release -p bricks-vms --bin cersei-envd --target x86_64-unknown-linux-musl

# 2. Build the image from the repository root.
docker build \
    -f crates/bricks-vms/docker/Dockerfile \
    -t cersei/sandbox-base:latest \
    --build-arg ENVD_BIN=target/x86_64-unknown-linux-musl/release/cersei-envd \
    .

# 3. Check that the binary is present. The daemon serves a socket when started,
#    so only test that the file exists and is executable.
docker run --rm --entrypoint /bin/sh cersei/sandbox-base:latest \
    -c 'test -x /usr/local/bin/cersei-envd && echo ok'
```

The image's default command keeps the container alive; commands then run through `docker exec`. Nothing in this crate starts the daemon inside the container. The crate ships no runnable example program: the recipes above are the tests you can adapt.

## Recipe 8: Mount a repository read-only

Useful for review agents that may read a project but must not change it. This is a Docker recipe, for the same reason as Recipe 2.

```rust
use bricks::vms::prelude::*;
use std::path::PathBuf;

async fn run() -> bricks::vms::Result<()> {
let opts = SandboxOpts::image("cersei/sandbox-base:latest").with_volume(VolumeMount {
    volume_id: VolumeId(PathBuf::from("/Users/me/projects/myrepo").display().to_string()),
    mount_path: "/work/repo".into(),
    read_only: true,
});

let sb = DockerRuntime::new()?.create(opts).await?;
let out = sb.commands().run(RunRequest::new("touch /work/repo/test.txt")).await?;
assert_ne!(out.exit_code, 0); // the read-only mount rejects the write
Ok(())
}
```
