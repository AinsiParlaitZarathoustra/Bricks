# Cookbook: General Agent

This recipe assembles a general-purpose agent from the parts of the SDK. Each part is optional, and the library does not add them for you: the `bricks` command-line tool and the desktop app do that wiring in their own session setup. Here it is written out, so you can see each piece.

## The complete setup

```rust
use async_trait::async_trait;
use bricks::prelude::*;
use bricks::mcp::McpServerConfig;
use bricks::memory::manager::MemoryManager;
use bricks::tools::lsp_tool::LspTool;
use std::sync::Arc;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let working_dir = std::env::current_dir()?;
    let selection = "my-provider/my-model";   // provider_id/model_id from ~/.bricks/providers.toml

    // 1. Provider
    let provider = bricks::provider_from_config(None, selection)?;

    // 2. Tools: every built-in tool, plus the LSP tool
    let mut tools = bricks::tools::all();
    tools.push(Box::new(LspTool::new(&working_dir)));

    // 3. Memory context for the system prompt: CLAUDE.md instructions and the MEMORY.md index
    let memory = MemoryManager::new(&working_dir);
    let memory_context = memory.build_context();

    // 4. MCP servers, started by the agent
    let filesystem = McpServerConfig::stdio("filesystem", "npx", &["-y", "@modelcontextprotocol/server-filesystem", "."]);

    // 5. The agent
    let agent = Agent::builder()
        .provider(provider)
        .tools(tools)
        .system_prompt(format!("You are a general coding agent.\n\n{memory_context}"))
        .max_tokens(16384)
        .auto_compact(true)
        .enable_broadcast(512)
        .working_dir(&working_dir)
        .session_id("general-session")
        .mcp_server(filesystem)
        .hook(LoggingHook)
        .build()?;

    let agent = Arc::new(agent);

    // 6. Run with streaming
    let mut stream = agent.run_stream("What files have changed since the last session?");
    while let Some(event) = stream.next().await {
        match event {
            AgentEvent::TextDelta(t) => print!("{t}"),
            AgentEvent::ToolStart { name, .. } => eprintln!("\n  [{name}]"),
            AgentEvent::Complete(_) => break,
            AgentEvent::Error(e) => {
                eprintln!("\nError: {e}");
                break;
            }
            _ => {}
        }
    }

    Ok(())
}
```

`bricks::tools::all()` includes the shell, file, web and planning tools (`coding()` plus `TodoWrite`).

<Callout type="warn">
An agent built without `.permission_policy(...)` or `.permission_profile(...)` runs every tool call: the builder's default is EXECUTE. Choose a policy that fits the task: `.permission_policy(DenyAll)` lets reads run and refuses what would be asked, and `.permission_profile(...)` sets ASK or CUSTOM rules.
</Callout>

<Callout type="warn">
The MCP server above is started with `npx`, and the package names are examples. Use servers you have checked, and give each one only the access it needs.
</Callout>

## Memory

`MemoryManager::build_context()` returns two parts, which the example puts into the system prompt:

- the **CLAUDE.md instruction files** of the working directory hierarchy;
- the **`MEMORY.md` index** of the memory files (the `memdir` folder).

The graph store is separate. Add graph results with `MemoryManager::recall` or `GraphMemory::recall`, as shown in [Graph Memory](/docs/cookbook-graph-memory#using-it-with-an-agent).

For a conversation that survives restarts, give the agent a conversation memory such as `JsonlMemory` and the same `session_id` on each start:

```rust
use bricks::memory::JsonlMemory;

let agent = Agent::builder()
    .provider(bricks::provider_from_config(None, selection)?)
    .tools(bricks::tools::coding())
    .memory(JsonlMemory::new("./sessions"))
    .session_id("general-session")
    .build()?;
```

With a memory attached and the same `session_id`, the history is loaded when the agent is built.

## Skills

A skill is a folder with a `SKILL.md` file. The skill service reads the skills installed in Bricks' store (`<bricks_home>/skills/`) and the one built-in skill, `create-skills`. It does not read `.agents/skills/` or `.claude/skills/` in a project or in your home folder; an application that wants those folders passes them explicitly. The agent sees each skill's name and description in a catalog, and activates one with the `Skill` tool to get its instructions. Activating a skill does not run anything by itself. For how the catalog is built and trusted, see `docs/skills.md` in the repository.

To give a library agent skills, pass a skill access to the builder with `skills(...)`. The `bricks` command-line tool does this from its configuration.

## MCP servers

`McpServerConfig::stdio(name, command, args)` starts a server that speaks MCP over standard input and output. The tools of each server are added next to the built-in tools:

```rust
use bricks::mcp::McpServerConfig;

let fs = McpServerConfig::stdio("fs", "npx", &["-y", "@modelcontextprotocol/server-filesystem", "."]);
let custom = McpServerConfig::stdio("my-server", "./my-mcp-server", &["--port", "8080"]);
```

Pass each one to the builder with `.mcp_server(config)`.

## Multi-turn conversation

```rust
let first = agent.run("Read the README and summarize the project").await?;
let second = agent.run("Now look at the test coverage").await?;
println!("{}", second.text());
```

The second call continues the first conversation. Without a memory attached, that history is kept only in the agent, so it is lost when the process ends.

## Lifecycle hooks

A hook runs at lifecycle events. Implement `events` (the events it wants) and `on_event`:

```rust
use bricks::hooks::{Hook, HookAction, HookContext, HookEvent};

struct LoggingHook;

#[async_trait]
impl Hook for LoggingHook {
    fn name(&self) -> &str { "logging" }

    fn events(&self) -> &[HookEvent] {
        &[HookEvent::PostToolUse]
    }

    async fn on_event(&self, ctx: &HookContext) -> HookAction {
        if let Some(tool) = &ctx.tool_name {
            println!("[hook] tool used: {tool}");
        }
        HookAction::Continue
    }
}
```

Add it with `.hook(LoggingHook)`. The hook sees the context of each event, and returns `HookAction::Continue` to let the agent proceed.

## Events for a custom interface

`enable_broadcast(capacity)` makes the agent publish its events, and `subscribe()` returns a receiver. It returns `None` when broadcast is not enabled, so unwrap it only after `enable_broadcast`:

```rust
let mut rx = agent.subscribe().expect("broadcast is enabled");

tokio::spawn(async move {
    while let Ok(event) = rx.recv().await {
        match event {
            AgentEvent::CostUpdate { cumulative_cost, .. } => update_cost_display(cumulative_cost),
            AgentEvent::TokenWarning { pct_used, .. } => show_context_warning(pct_used),
            _ => {}
        }
    }
});
```

`update_cost_display` and `show_context_warning` stand for your interface code.
