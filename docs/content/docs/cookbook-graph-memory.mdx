# Cookbook: Graph Memory

`GraphMemory` keeps memories as nodes of an embedded graph database (Grafeo). Each memory has a type, a confidence and a decay rate, and can be tagged by topic and linked to other memories. It is a separate store from the conversation memories of `JsonlMemory`.

<Callout type="warn">
Graph memory is behind the `graph` feature of the `bricks-memory` crate. The `bricks` facade does not enable it, so add the crate to your own `Cargo.toml`:

```toml
bricks-memory = { version = "0.6", features = ["graph"] }
```

The `structured` feature enables `graph` too, and adds the long-term structured memory that the `bricks` command-line tool uses.
</Callout>

## Setup

```rust
use bricks::memory::graph::GraphMemory;
use bricks::memory::memdir::MemoryType;
use std::path::Path;

// Open or create the database file
let graph = GraphMemory::open(Path::new("./memory.db"))?;

// Or keep it in memory, for tests
let graph = GraphMemory::open_in_memory()?;
```

## Storing memories

`store_memory` takes the text, a `MemoryType` (`User`, `Feedback`, `Project` or `Reference`) and a confidence from 0 to 1. It returns the new memory's id.

```rust
let id = graph.store_memory(
    "User prefers concise responses without emojis",
    MemoryType::User,
    0.95,
)?;

let id2 = graph.store_memory(
    "Authentication uses JWT with RS256, stored in HttpOnly cookies",
    MemoryType::Project,
    0.9,
)?;

let id3 = graph.store_memory(
    "Don't add docstrings to code the user didn't change",
    MemoryType::Feedback,
    1.0,
)?;
```

## Tagging and linking

```rust
// Tag a memory with topics
graph.tag_memory(&id2, "authentication")?;
graph.tag_memory(&id2, "security")?;

// Link two related memories; the relationship name is free text
graph.link_memories(&id2, &id3, "RELATES_TO")?;

let id4 = graph.store_memory(
    "API rate limiting: 100 req/min per user, 1000 req/min per org",
    MemoryType::Project,
    0.85,
)?;
graph.tag_memory(&id4, "security")?;
graph.link_memories(&id2, &id4, "RELATES_TO")?;
```

## Querying

```rust
// Text recall: the best matches for the query, at most `limit`
let results: Vec<String> = graph.recall("authentication", 5);

// The same, with a score for each match
let scored: Vec<(String, f32)> = graph.recall_top_k("authentication", 5);

// By type
let user_prefs = graph.by_type(MemoryType::User);
let project_docs = graph.by_type(MemoryType::Project);

// By topic
let security_memories = graph.by_topic("security");
```

`recall`, `recall_top_k`, `by_type` and `by_topic` return plain values, not `Result`.

## Confidence decay

Each memory records a `decay_rate` (0.01 per day by default) and the time it was last validated. Its effective confidence is:

```text
effective = confidence - decay_rate × days since last validation     (clamped to 0..1)
```

A memory that nobody validates loses confidence over time, so old information stops outranking new information. `revalidate_memory` sets the validation time to now:

```rust
let still_valid = graph.revalidate_memory(&id)?;   // false when the id does not exist
```

## Session recording

```rust
graph.record_session(
    "session-abc123",
    Some("my-provider/my-model"),   // the model, optional
    15,                             // turns
)?;
```

The schema defines `PRODUCED` edges from sessions to memories (see the storage layout below).

## Schema versions

The database is checked when it is opened, and migrated when needed. `schema_version` reports the state:

```rust
use bricks::memory::graph::VersionCheck;

match graph.schema_version() {
    VersionCheck::UpToDate => println!("schema is current"),
    VersionCheck::NeedsMigration { from, to } => println!("schema v{from} to v{to} needed"),
    VersionCheck::CodeBehind { graph_version, code_version } => {
        println!("database v{graph_version} is newer than this code (v{code_version})")
    }
}
```

Migrations run in order. Version 2 adds the decay fields (`last_validated_at`, `decay_rate`, `embedding_model_version`) to memories, and version 3 adds the structured memory nodes used by the long-term memory.

## Using it with an agent

`GraphMemory` is not a conversation memory, so it cannot be passed to `Agent::builder().memory(...)`. Put recalled text into the system prompt yourself. `MemoryManager::build_context()` returns the project's `CLAUDE.md` instructions and the `MEMORY.md` index of the memory files. It does not include graph recall, so add graph results to the prompt with `recall`:

```rust
use bricks::memory::manager::MemoryManager;
use std::path::Path;

let mm = MemoryManager::new(Path::new("./project"))
    .with_graph(Path::new("./memory.db"))?;

let context: String = mm.build_context();                 // CLAUDE.md instructions and MEMORY.md index
let recalled = mm.recall("coding style preferences", 5);  // graph memories for this question

let agent = Agent::builder()
    .provider(bricks::provider_from_config(None, "my-provider/my-model")?)
    .tools(bricks::tools::coding())
    .system_prompt(format!(
        "You are a coding agent.\n\n{context}\n\nKnown preferences:\n{}",
        recalled.join("\n")
    ))
    .build()?;
```

## Storage layout

| Node | Properties | Meaning |
|------|-----------|---------|
| `Memory` | `content`, `mem_type`, `confidence`, `created_at`, `updated_at`, `last_validated_at`, `decay_rate`, `embedding_model_version` | A stored memory |
| `Session` | `session_id`, `started_at`, `model`, `turns` | A recorded session |
| `Topic` | `name` | A tag shared by memories |

| Edge | From → To | Meaning |
|------|-----------|---------|
| `RELATES_TO` | Memory → Memory | A link with a `relationship` name and a `weight` |
| `TAGGED` | Topic → Memory | The memory belongs to the topic |
| `PRODUCED` | Session → Memory | The session produced the memory |

Benchmarks of this store are not in this recipe. The repository does not hold a dated measurement report for it.
