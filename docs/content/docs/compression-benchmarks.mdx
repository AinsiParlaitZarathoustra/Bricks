# Compression Benchmarks

A live-LLM integration test ships with the SDK (`crates/bricks-agent/tests/e2e_live_compression.rs`). It runs the **same prompt, same tool, same fixture** twice — once with `CompressionLevel::Off`, once with `CompressionLevel::Aggressive` — and compares the provider-reported `input_tokens`. Off is a verified byte-for-byte passthrough, so the delta is the measured savings.

## TL;DR

| Provider | Model | Off → Aggressive (input tokens) | **Savings** | tool_calls | turns |
|---|---|---|---|---|---|
| **OpenAI** | `gpt-4o-mini` | **11,576 → 8,202** | **29.1%** | 15 → 13 | 5 → 5 |
| **Google Gemini** | `gemini-2.5-flash` | **4,490 → 1,700** | **62.1%** | 1 → 1 | 5 → 3 |

The test asserts `aggressive < off` and `savings ≥ 10%` on real provider bills. The numbers above were captured on 2026-04-20 with an earlier harness (`e2e_openai_compression`), which is no longer in the repository.

<Callout type="warn">
These figures were measured on 2026-04-20, before each `Bash` call ran in its own process (commit `4263cd9`). The tool output that reaches the compressor now comes through that path, so rerun the live test before quoting these numbers as current.
</Callout>

<Callout type="info">
Savings ratios are **not fixed** — they depend on how much of the turn's context is tool output versus system prompt + tool schemas + assistant turns. OpenAI's `gpt-4o-mini` happened to loop on 13–15 tool calls (each re-paying schema tax), Gemini's `gemini-2.5-flash` made a single clean tool call, so Gemini's ratio is closer to the raw byte-level win.
</Callout>

## Synthetic fixture baselines

Fast, deterministic, no API key needed. Run:

```bash
cargo test -p bricks-compression
```

The corpus tests check these properties:

| Check | Test (`crates/bricks-compression/tests/corpus.rs`) |
|---|---|
| Every captured and reconstructed fixture keeps the lines a reader needs, names its saved original, and does not grow | `every_fixture_keeps_what_matters_and_names_its_original` |
| `Off` returns ordinary outputs byte for byte | `off_level_is_exact_passthrough_for_ordinary_outputs` |
| Small outputs that barely shrink are returned unchanged | `small_outputs_that_barely_shrink_are_left_alone` |

No test asserts a minimum savings percentage on these fixtures; the savings figures on this page come from the live runs below.

## Live provider benchmarks

The live test is `#[ignore]` by default, so `cargo test --workspace` makes no paid calls. Without `BRICKS_LIVE_MODEL` it prints a notice and passes. With it, the test calls the model you name, as `provider_id/model_id` from your `providers.toml` (`BRICKS_LIVE_CONFIG` selects another file). The API key is read from the environment variable named by that provider's `api_key_env`.

<Tabs items={['OpenAI', 'Gemini']}>
<Tab value="OpenAI">
```bash
BRICKS_LIVE_MODEL=<provider_id>/gpt-4o-mini \
  cargo test -p bricks-agent --test e2e_live_compression \
    compression_reduces_the_real_token_bill \
    -- --ignored --nocapture
```

**What we got (2026-04-20, `gpt-4o-mini`, earlier harness):**

```
── openai run 1: CompressionLevel::Off ──
  off       : input=11576  output=276  total=11852  tool_calls=15  turns=5

── openai run 2: CompressionLevel::Aggressive ──
  aggressive: input=8202   output=276  total=8478   tool_calls=13  turns=5

── openai compression saved 29.1% of input tokens (11576 → 8202) ──
```
</Tab>
<Tab value="Gemini">

## Intercept per-call compression logs

Every compression call emits a `tracing::info!` event on the `bricks_compression` target. In your own program, install a `tracing` subscriber filtered on `bricks_compression=info` (see the [overview](/docs/compression-overview)). The `bricks` binary installs no subscriber, so `RUST_LOG` has no effect on it. Bricks sets the level with `[compression] level` in `bricks.toml`.

Sample line from the Gemini run:

```
INFO bricks_compression: tool-output compressed
  tool="Bash" level=aggressive strategy="shell" detail="cargo-test"
  before_bytes=2893 after_bytes=1565
  before_lines=76 after_lines=30
  savings_pct="45.9"
```

Each call exposes: `tool`, `level`, `strategy` (the route taken, such as `shell`, `web` or `passthrough`), `detail` (rule name or detected `Language`), byte counts, line counts, and `savings_pct`. Full field reference on the [Compression Overview](/docs/compression-overview#observability).

## Synthetic vs live — why they differ

Synthetic tests measure the **pipeline in isolation**: input → compress → output. Live tests measure the **full turn the LLM bills you for**: system prompt + tool schemas + previous assistant turns + compressed tool result.

Compression only touches the tool-result content. It cannot rewrite the assistant's own messages, the system prompt, or the JSON Schema sent for every tool definition. So the real-world ratio is always *at most* the synthetic ratio, and typically **lower**.

Concretely for the Gemini run above:
- Uncompressed tool result ≈ 2,893 bytes → after Aggressive: 1,565 bytes (−45.9% at the byte level).
- The 2,790-token billing delta (4,490 − 1,700) matches that shrink almost exactly because Gemini only called the tool once. There's no other noise on the turn.

For the OpenAI run:
- Uncompressed tool result contributes the same 2,893 bytes *per call*, but `gpt-4o-mini` issued 13–15 tool calls. Each re-pays the `Bash` JSON schema + system prompt on the request side, diluting the savings ratio.
- Absolute win is still large: −3,374 input tokens per run.

## Regression guard

`bricks-compression/tests/corpus.rs::off_level_is_exact_passthrough_for_ordinary_outputs` checks **byte-for-byte identity** when the level is `Off`. This makes the feature opt-in: users who don't change their builder chain, their CLI flags, or their config file see no difference.

## Hardware + reproducibility caveats

- The live numbers above were captured on an **Apple M1 Pro** against the current production OpenAI / Google endpoints on **2026-04-20**.
- Token counts are **provider-reported**, not our estimate (`output.usage.input_tokens` straight from `OpenAI` / `usageMetadata.promptTokenCount` from Gemini).
- `gpt-4o-mini`'s tool-call loop count is non-deterministic — expect ±2 tool calls across reruns, which shifts OpenAI savings within roughly ±8%. Gemini's single-call pattern is stable.
