# Workflows

A workflow is a pipeline you define as a graph of **steps**, instead of leaving the order of work to one agent's reasoning. You decide what runs, in what order, how data moves between steps, and what happens on a branch or a failure. A step can call a Rust function, an [agent](/docs/api-agent), a [tool](/docs/api-tools), or another workflow.

The defining property of `bricks-workflows` is that **the whole workflow is data**. A workflow is a `WorkflowDef`, a list of nodes and edges, which round-trips to and from JSON without loss. A visual editor can therefore emit the same JSON that the programmatic builder produces, and the runtime executes both the same way.

<Callout type="warn">
**Library only, for now.** `bricks-workflows` is enabled with `features = ["workflows"]` on the `bricks` facade. Neither the `bricks` command-line tool nor the desktop app runs workflows, and this repository contains no visual editor. The JSON format is designed for one, but the editor is not part of this codebase.
</Callout>

## When to use a workflow

Use a workflow when the steps are known in advance and their order matters: you control the data flow and the primitive used at each stage. Use a plain [`Agent`](/docs/api-agent) when the path is open and the model should decide the next step. They combine: a workflow step can run an agent, and an agent can be given a workflow as a tool.

## The shape of a workflow

```text
  input ──▶ [validate] ──▶ ⟨branch⟩ ──when premium──▶ [enrich] ──▶ [summarize] ──▶ result
                              │
                              └──────else───────────▶ [summarize] ─────────────────▶ result

  parallel block:
                 ┌─▶ [fetch_a] ─┐
  input ──▶ «par»┤              ├─▶ «join» ──▶ [merge] ──▶ result
                 └─▶ [fetch_b] ─┘
```

The node kinds of a `WorkflowDef`:

- **Step**: runs a registered step by id (a function, an agent, a tool or a nested workflow).
- **Parallel and join**: runs branches concurrently, then collects them with `AllOrFail` or `AllSettled`.
- **Branch**: tests conditions in order; the first match wins.
- **Loop**: `DoWhile`, `DoUntil`, or `ForEach` with a concurrency limit.
- **Map**: a pure JSON reshape between steps.

## Core pieces

<Cards>
  <Card title="WorkflowDef (the IR)">
    A serializable `{ id, nodes, edges, entry }` graph. The builder and any editor produce it. `UiHints` (position, label, colour) are carried along and ignored when the workflow runs.
  </Card>
  <Card title="Step trait">
    Shaped like a [`Tool`](/docs/api-tools): an id, input and output JSON schemas, and an async `execute`. The built-in steps are `FnStep`, `AgentStep`, `ToolStep` and `WorkflowStep`.
  </Card>
  <Card title="StepRegistry">
    Maps step ids to implementations. The JSON names steps by id only, and the host supplies the code. `catalog()` lists the available steps with their schemas.
  </Card>
  <Card title="WorkflowEvent and WorkflowStream">
    Serializable events (`StepStarted`, `StepCompleted`, `BranchTaken`, `StateUpdated`, …) that a host can forward to a client.
  </Card>
</Cards>

## A first workflow

Register the steps, write the graph, compile it against the registry, and run it.

```rust
use bricks::workflows::prelude::*;
use serde_json::json;
use std::sync::Arc;

#[tokio::main]
async fn main() -> bricks::types::Result<()> {
    // 1. Register executable steps by id.
    let registry = StepRegistry::new();
    registry.register(Arc::new(FnStep::new("upper", |input, _ctx| async move {
        let s = input.get("message").and_then(|v| v.as_str()).unwrap_or("");
        Ok(json!({ "message": s.to_uppercase() }))
    })));
    registry.register(Arc::new(FnStep::new("emphasize", |input, _ctx| async move {
        let s = input.get("message").and_then(|v| v.as_str()).unwrap_or("");
        Ok(json!({ "message": format!("{s}!!!") }))
    })));

    // 2. Write the graph. The same WorkflowDef can be produced as JSON by an editor.
    let def = WorkflowBuilder::new("greet")
        .then("upper")
        .then("emphasize")
        .commit();

    // 3. Compile against the registry, then run.
    let wf = Workflow::compile(def, &registry)?;
    let result = wf.start(json!({ "message": "hello world" })).await?;

    assert_eq!(result.status, RunStatus::Success);
    println!("{}", result.result.unwrap()); // {"message":"HELLO WORLD!!!"}
    Ok(())
}
```

## Round-tripping as JSON

The builder's output is plain serde data:

```rust
let def = WorkflowBuilder::new("greet").then("upper").then("emphasize").commit();

let wire = serde_json::to_string(&def)?;     // store it, or send it to an editor
let same: WorkflowDef = serde_json::from_str(&wire)?;
assert_eq!(def, same);
```

The JSON for the two-step workflow above looks like this (node kinds are externally tagged, and `config` is omitted when null):

```json
{
  "id": "greet",
  "entry": "upper_1",
  "nodes": [
    { "id": "upper_1",     "kind": { "step": { "step_id": "upper" } } },
    { "id": "emphasize_2", "kind": { "step": { "step_id": "emphasize" } } }
  ],
  "edges": [
    { "from": "upper_1", "to": "emphasize_2", "kind": "then" }
  ]
}
```

<Callout type="warn">
The IR enums are **externally tagged** on purpose (`{ "step": { … } }`, and `"then"` for a unit variant). Internally tagged serde enums go through a content buffer, which overflows the recursion limit of `serde_json` on serialization. Keep the tagging as it is.
</Callout>

## Live status

`stream()` returns a `WorkflowStream` of `WorkflowEvent`s. Each event is `Serialize`, so a host can send it to a client over SSE or a WebSocket.

```rust
let wf = Workflow::compile(def, &registry)?;   // Arc<Workflow>
let mut stream = wf.stream(json!({ "message": "hi" }));

while let Some(event) = stream.next().await {
    let frame = serde_json::to_string(&event)?;
    // send `frame` to the client
}
```

## Enable the feature

```toml
[dependencies]
bricks = { version = "0.6", features = ["workflows"] }
```

Then `use bricks::workflows::prelude::*;`. The main types are also re-exported at the top level of `bricks::workflows`.
