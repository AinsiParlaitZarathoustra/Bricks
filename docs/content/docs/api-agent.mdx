# bricks-agent

The high-level Agent API. Builder pattern for configuration, an agentic loop that handles tool dispatch and multi-turn conversations, a set of 36 event variants for observation, and automatic context management.

<Callout type="info">
Most users interact with Bricks through this crate. The `bricks` facade re-exports `Agent`, `AgentBuilder`, `AgentOutput`, `AgentEvent`, and `AgentStream` directly.
</Callout>

---

## Agent Builder

Every agent starts with a builder. The only required field is `.provider()` — everything else has sensible defaults. The provider is one model configured in `~/.bricks/providers.toml`, selected as `provider_id/model_id`.

```rust
let agent = Agent::builder()
    .provider(bricks::provider_from_config(None, "my-provider/my-model")?)
    .tools(bricks::tools::coding())
    .system_prompt("You are a coding assistant.")
    .max_tokens(16384)
    .permission_policy(AllowAll)
    .build()?;
```

## Execution Modes

### One-Shot (shorthand)

The simplest way to run an agent — builds, executes, and returns in one call:

```rust
let output = Agent::builder()
    .provider(bricks::provider_from_config(None, "my-provider/my-model")?)
    .tools(bricks::tools::coding())
    .run_with("Fix the failing tests")
    .await?;

println!("{}", output.text());
println!("Turns: {}, Tool calls: {}", output.turns, output.tool_calls.len());
```

### Reusable agent (multi-turn)

`run` is async. Build once, run multiple times. The agent maintains conversation history across calls:

```rust
let agent = Agent::builder()
    .provider(bricks::provider_from_config(None, "my-provider/my-model")?)
    .tools(bricks::tools::coding())
    .build()?;

// First turn
let output1 = agent.run("What files are in src/?").await?;

// Second turn — the agent remembers the first
let output2 = agent.run("Now fix the bug in main.rs").await?;
```

### Streaming (events in real-time)

`run_stream` takes the agent behind an `Arc`, so the run can outlive the caller's stack frame. It returns an `AgentStream` that yields events as they happen. `AgentStream::cancel()` is applied to the run. `respond_permission()` and `inject_message()` are accepted by `AgentStream`, but `run_stream_input` ignores their control messages (`crates/bricks-agent/src/lib.rs:286-287`), so they have no effect in this version.

```rust
use std::sync::Arc;

let agent = Arc::new(agent);
let mut stream = agent.run_stream("Deploy the application");

while let Some(event) = stream.next().await {
    match event {
        AgentEvent::TextDelta(t) => print!("{t}"),
        AgentEvent::ThinkingDelta(t) => { /* thinking content */ }
        AgentEvent::ToolStart { name, input, .. } => {
            eprintln!("\n[Tool: {name}]");
        }
        AgentEvent::ToolEnd { name, duration, is_error, .. } => {
            let status = if is_error { "FAIL" } else { "OK" };
            eprintln!("[{name}: {status} in {} ms]", duration.as_millis());
        }
        AgentEvent::PermissionRequired(req) => {
            // respond_permission() has no effect in this version (see note above)
            eprintln!("Permission requested for {}", req.tool_name);
        }
        AgentEvent::Complete(output) => {
            eprintln!("\nDone: {} turns", output.turns);
            break;
        }
        AgentEvent::Error(msg) => {
            eprintln!("Error: {msg}");
            break;
        }
        _ => {}
    }
}
```

## AgentEvent

36 variants covering every observable moment in the agentic loop. The most useful are listed below; the enum in `bricks_agent::events` is the reference.

### Content Events

| Variant | Fields | Emitted When |
|---------|--------|-------------|
| `TextDelta(String)` | text chunk | Model streams a text token |
| `ThinkingDelta(String)` | thinking chunk | Model streams a reasoning token |

### Tool Events

| Variant | Fields | Emitted When |
|---------|--------|-------------|
| `ToolStart { name, id, input }` | tool name, call ID, JSON input | Tool dispatch begins |
| `ToolProgress { name, message }` | tool name, progress message | A running tool reports progress |
| `ToolEnd { name, id, result, is_error, duration, compression }` | tool name, call ID, result text, error flag, wall-clock time, compression stats | Tool execution completes |
| `ToolPermissionCheck { name, id, level }` | tool name, call ID, permission level | A tool call is checked against the policy |

### Lifecycle Events

| Variant | Fields | Emitted When |
|---------|--------|-------------|
| `TurnStart { turn }` | turn number | A model call begins |
| `TurnComplete { turn, stop_reason, usage }` | turn number, stop reason, token usage | One model call + tool cycle finishes |
| `ModelRequestStart { turn, message_count, token_estimate }` | turn, messages sent, estimated tokens | A request is about to be sent |
| `TokenWarning { pct_used, state }` | context % used, `Normal`/`Warning`/`Critical` | Context window approaching limit |
| `CompactStart { reason, messages_before }` | compaction reason, message count | Context compaction begins |
| `CompactEnd { messages_after, tokens_freed }` | remaining messages, tokens reclaimed | Compaction finishes |
| `CompactionResult { reason, outcome }` | reason, `CompactionOutcome` | The outcome is explicit: `Compacted`, `InsufficientGain`, `Failed`, `Skipped` |
| `SessionLoaded { session_id, message_count }` | session ID, number of messages | Session resumed from memory |
| `SessionSaved { session_id }` | session ID | Session stored |

### Control Events

| Variant | Fields | Emitted When |
|---------|--------|-------------|
| `PermissionRequired(PermissionRequest)` | tool name, input, description, level, id | Tool needs approval (interactive policy) |
| `ApprovalRequested` / `ApprovalResolved` | approval and decision details | An approval is asked and answered (`control` contract) |
| `EditApplied { tool_call_id, tool, files }` | call ID, tool, changed files | A file change was written |
| `CostUpdate { turn_cost, cumulative_cost, input_tokens, output_tokens }` | costs and token counts | After each model call |
| `SubAgentSpawned { agent_id, prompt }` | sub-agent ID, task description | Sub-agent created |
| `SubAgentComplete { agent_id, result }` | sub-agent ID, `AgentOutput` | Sub-agent finished |
| `SkillActivated` / `SkillNotActivated` | skill name, source, revision or reason | An Agent Skill was activated or refused |

### Terminal Events

| Variant | Fields | Emitted When |
|---------|--------|-------------|
| `Status(String)` | status message | Informational update |
| `Error(String)` | error message | Unrecoverable error |
| `Complete(AgentOutput)` | final output | Agent loop finished |

## Reasoning Profiles

Reasoning depth is not a fixed SDK enum. A model declares its own profiles in `providers.toml`, and an agent selects one by id. Bricks has no list of levels, and the id sent to the server is the profile's `parameters`, not its local name:

```toml
[[providers.models.reasoning.profiles]]
id = "approfondi"
label = "Approfondi"
parameters = { reasoning_effort = "high" }
```

```rust
let agent = Agent::builder()
    .provider(bricks::provider_from_config(None, "my-provider/my-model")?)
    .reasoning_profile("approfondi")   // must be a profile of this model
    .build()?;

println!("{:?}", agent.reasoning_profile());   // the effective profile id, if any
agent.set_reasoning(None);                     // back to the model's declared default
```

Passing an id the model does not declare is an error that lists the available ones. See [bricks-provider](/docs/api-provider) for the protocol side.

## Auto-Compact

When the conversation approaches the context window limit, the agent summarizes older messages to free space. This happens transparently — the model continues working without interruption. Auto-compact is on by default.

```rust
Agent::builder()
    .auto_compact(true)           // default
    .compact_threshold(0.85)      // trigger at 85% of the context window
    .tool_result_budget(50_000)   // default: tool results beyond 50K chars are replaced by a placeholder
```

The compaction pipeline:
1. Measure the active context, with its provenance (`measured`, `counted`, `mixed` or `estimated`)
2. Above the threshold, ask the model for a budgeted summary with fixed headings: objective, constraints, decisions, files, actions, open problems, key facts
3. Keep the user's messages verbatim
4. Replace the old messages only if the summary gains enough space; otherwise the outcome is `InsufficientGain`, and nothing is replaced
5. Keep the original history in memory (`raw_history()`, `compaction_snapshots()`). When a session memory is configured, the raw history and each snapshot are also stored (`<id>.raw`, `<id>.compaction-<n>`), see `crates/bricks-agent/src/runner.rs:1958-1975`

Events emitted: `CompactStart`, `CompactEnd` (with `messages_after` and `tokens_freed`), and `CompactionResult` with the explicit outcome.

## System Prompt Caching

The system prompt is split into two sections separated by `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` (`__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__`):

```
[Static section — cached by the provider]
__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__
[Dynamic section — rebuilt each turn]
```

```rust
Agent::builder()
    .system_prompt("You are a coding assistant. Always use Rust.")  // static, cached
    .append_system_prompt("Current time: 2024-01-01")               // dynamic, per-turn
```

Providers that support prompt caching cache everything before the boundary. Whether caching applies depends on the model's protocol and its `compat` settings (`prompt_cache_markers` for `anthropic_messages`). See `docs/providers.md` in the repository.
