# Sandboxes & VMs

`bricks-vms` is the crate that provides a **sandbox runtime layer** for Bricks ADK. A sandbox is an environment in which commands run and files are read and written, separate from the host filesystem and process namespace. The same crate provides three **host-mediated primitives** — `Volume`, `Mailbox`, `KvStore` — that let several sandboxes exchange files and messages and share key/value state.

<Callout type="warn">
**Nothing here is on by default in a session.** The crate is compiled by the default `vms` feature of the `bricks` facade, but the `bricks` command-line tool and the desktop app do not create sandboxes, do not register the agent-facing VM tools, and do not expose a backend choice. Sandboxes are used when you assemble an agent yourself in Rust. See [What is wired today](#what-is-wired-today).
</Callout>

## A minimal example

```rust
use bricks::vms::prelude::*;

#[tokio::main]
async fn main() -> std::result::Result<(), Box<dyn std::error::Error>> {
    // A local runtime: plain host processes, no isolation.
    let runtime = LocalProcessRuntime::new()?;

    // Allocate a sandbox from an image name.
    let sb = runtime
        .create(SandboxOpts::image("cersei/sandbox-base:latest"))
        .await?;

    let out = sb.commands().run(RunRequest::new("echo hello && pwd")).await?;
    println!("{} (exit {})", out.stdout.trim(), out.exit_code);

    sb.filesystem().write("/work/note.txt", b"first-party").await?;
    let bytes = sb.filesystem().read("/work/note.txt").await?;
    assert_eq!(&bytes[..], b"first-party");

    // Snapshot, kill, restore.
    let snap = sb.snapshot().await?;
    sb.kill().await?;
    let restored = runtime.restore(&snap).await?;
    let again = restored.filesystem().read("/work/note.txt").await?;
    assert_eq!(&again[..], b"first-party");
    Ok(())
}
```

`cersei/sandbox-base:latest` is the default image name. It is only meaningful with `DockerRuntime`: the local backend ignores the image and runs on the host.

## Architecture

```text
 host process (your agent)
 ├── Agent ── tools ── Bash (routes to the sandbox when one is in ToolContext.extensions)
 │                 └── vm_tools (only if you add them to the tool list)
 ├── Mailbox, KvStore (host-side; one broker per runtime, shared by its sandboxes)
 ├── SnapshotRegistry  (~/.cersei/vms/snapshots)
 └── SandboxRuntime
       ├── LocalProcessRuntime  -> ~/.cersei/vms/local/<sandbox-id>/rootfs/
       └── DockerRuntime        -> docker CLI -> container "cersei-vm-<sandbox-id>"
```

Sandboxes do not talk to each other over the network. Messages and shared values go through the host broker, which is the only path between sandboxes.

## What is wired today

| Area | State |
|---|---|
| `bricks` command-line tool and desktop app | No sandbox is created, no backend is chosen, and no VM tool is registered. Their session tools are `bricks_tools::coding()` (filesystem, shell, web) plus the native sub-agent tools when `[agents] enabled`. |
| `Bash` tool | Routes through a sandbox when the caller inserts an `Arc<dyn Sandbox>` into `ToolContext.extensions`. The background, `yield_time_ms` and `ready_pattern` options are refused there. |
| `vm_tools` (five agent-facing tools) | Compiled with the `vms` feature. They are not in `bricks_tools::all()` or `coding()`: add them to the tool list yourself. See [the API page](/docs/vms-api#agent-facing-tools-bricks_toolsvm_tools). |
| Sub-agents | `SandboxAllocator` and `DefaultAllocator` exist, but no agent code uses them. Each sub-agent runs on the host. |
| AgentRL | The production runner isolates proposals in temporary copies of the working directory, not in sandboxes. See [AgentRL](/docs/agentrl-overview). |
| AgentLang | `io.*` and `net.*` use the host tools. A sandbox in the context only sets the program's identity. See [AgentTemplate](/docs/agentrl-template). |

## Not implemented

These are absent from the code, not merely undocumented:

- `Filesystem::watch` on both backends (returns an error).
- Pause and resume on the public capability flags (`pause_resume` is `false` for both backends, although `DockerRuntime` has the code).
- Stdin for streamed commands: streams are output-only.
- Sandbox access to `Mailbox` and `KvStore` from inside a container. The `cersei-envd` daemon in the crate speaks a small protocol, but neither backend connects to it.
- The `backend-firecracker` and `backend-e2b` features: reserved, with no code behind them.
- Incremental snapshots and snapshot garbage collection.
- A command-line option or configuration key that selects a sandbox backend.
