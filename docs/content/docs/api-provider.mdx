# bricks-provider

Abstraction over LLM backends. A provider is one model declared in `~/.bricks/providers.toml` and driven by one of three wire protocols (`chat_completions`, `responses`, `anthropic_messages`). Every provider implements streaming completion and reports the context window of its model (`context_window`). A provider built from configuration also exposes the model's declared limits through `model_info()` (`crates/bricks-provider/src/lib.rs:204-235`).

## Provider Trait

```rust
use bricks::provider::{CompletionResponse, CompletionStream, ImageTransport, ModelInfo, ProviderOptions, RequestIdentity};
#[async_trait]
pub trait Provider: Send + Sync {
    fn name(&self) -> &str;
    fn context_window(&self, model: &str) -> u64;
    fn model_info(&self) -> Option<ModelInfo> { None }
    fn request_identity(&self, options: &ProviderOptions) -> Option<RequestIdentity> { None }
    fn image_transport(&self) -> ImageTransport { ImageTransport::None }
    async fn complete(&self, request: CompletionRequest) -> Result<CompletionStream>;
    async fn complete_blocking(&self, request: CompletionRequest) -> Result<CompletionResponse>; // default: complete + collect
    async fn count_request_tokens(&self, request: &CompletionRequest) -> Result<Option<u64>>;   // default: Ok(None)
}
```

`count_request_tokens` returns `Ok(None)` when no token-counting endpoint is configured for the model; callers then fall back to a local estimate.

`request_identity` names what a request with these `ProviderOptions` is sent as: `api_model`, the model name in the request body, and the reasoning profile applied (`None` when there is none). A configured provider resolves it the way its request body is built; a custom provider returns `None` unless it overrides the method, and the prompt's model block then carries only the Bricks selection and profile. The server may still run another model behind an alias.

`image_transport` says how an image a tool returns (`ToolResult::with_images`) can reach the model: `ImageTransport::ToolResult` (inside the tool result), `UserTurn` (after the results, in the same user turn) or `None` (not shown, the result says so). A configured provider derives it from the model's `input_modalities` and the protocol; the default is `None`. See [Multimodal Input](/docs/multimodal#images-returned-by-tools).

## Configured Providers

Nothing is built in. Models are selected explicitly as `provider_id/model_id`, and the provider is never inferred from the model name.

```rust
use bricks::provider::{provider_from_config, ProviderRegistry};

// Read ~/.bricks/providers.toml and build the provider for one model
let provider = provider_from_config(None, "custom/flash")?;

// Or resolve first, then choose a reasoning profile and a price tariff
let registry = ProviderRegistry::load(Some("./providers.json".as_ref()))?;
let model = registry.resolve("custom/flash")?;
let provider = model
    .provider()
    .reasoning_profile("approfondi")   // a profile defined for this model in the file
    .tariff("offpeak")                 // optional: a named price variant
    .build()?;                         // reads api_key_env now
```

`ProviderRegistry::load(None)` reads `~/.bricks/providers.toml`; an explicit path replaces it. A missing or invalid file is an error, and there is no fallback.

| Type | Role |
|---|---|
| `ProviderRegistry` | The loaded configuration. `models()` lists every model in file order; `resolve(selection)` returns a `ResolvedModel`. |
| `ResolvedModel` | One configured model. `provider()` returns a `ProviderBuilder`; `build_provider()` builds with the defaults; `selection()` gives `provider_id/model_id`. |
| `ProviderBuilder` | `reasoning_profile(id)`, `tariff(name)`, `env(lookup)`, `http_client(client)`, `build()`. |
| `ConfiguredProvider` | The `Provider` implementation for one model. `model()` returns its `ResolvedModel`; `estimate_cost(&Usage)` returns `Option<CostEstimate>`, `None` when no price is known (`crates/bricks-provider/src/provider.rs:269`). |

## Protocols

| Protocol | Relative path | Conventional auth |
|---|---|---|
| `chat_completions` | `chat/completions` | `bearer` |
| `responses` | `responses` | `bearer` |
| `anthropic_messages` | `messages` | `api_key_header` (`x-api-key`) |

The protocol is set per provider and can be overridden per model. The key is read from the environment variable named by `api_key_env`, or taken from an inline `api_key` for a local setup.

## ModelInfo and Limits

```rust
pub struct ModelInfo {
    pub selection: String,           // provider_id/model_id
    pub protocol: &'static str,
    pub limits: ModelLimits,
    pub reasoning_resent: bool,      // reasoning in the history is sent back, so it occupies the context
    pub token_counting: bool,        // a counting endpoint is configured
}

pub struct ModelLimits {
    pub max_input_tokens: u64,
    pub max_output_tokens: u64,
}
```

The limits are declared in the configuration. They never change what the server enforces; Bricks uses them to cap `max_tokens` and to budget the prompt.

## CompletionRequest

A provider request. Its public fields are `model`, `messages`, `system`, `tools`, `max_tokens`, `temperature`, `stop_sequences`, `options` and `output_modalities` (empty means text only).

```rust
use bricks::provider::CompletionRequest;

let request = CompletionRequest::new("vendor-flash"); // max_tokens defaults to 16384
```

`ProviderOptions` carries the engine-level options an adapter understands: `tool_choice = "required"` (a forced tool call) and `reasoning_profile` (the profile id for this call). Everything else a model needs is configuration, not a request option.

```rust
let mut options = ProviderOptions::default();
options.set("tool_choice", "required");
options.set("reasoning_profile", "approfondi");
```

## Custom Provider

Implement `Provider` for a backend that is not covered by the three protocols:

```rust
use bricks::provider::CompletionStream;
struct MyProvider;

#[async_trait]
impl Provider for MyProvider {
    fn name(&self) -> &str { "my-llm" }
    fn context_window(&self, _model: &str) -> u64 { 128_000 }
    async fn complete(&self, request: CompletionRequest) -> Result<CompletionStream> {
        todo!("your implementation: a call to your service")
    }
}
```

`complete_blocking`, `count_request_tokens` and `model_info` have default implementations. For a service that speaks one of the three protocols, a `providers.toml` entry is enough and no code is needed.

## Removed API

The `Anthropic`, `OpenAi` and `Gemini` clients, `Auth`, `AuthProvider`, `OAuthToken`, `from_model_string` and the built-in model registry were removed in 0.3.6. There is no `from_env()` constructor and no environment-variable fallback. See [Providers](/docs/providers) and [Migration](/docs/migration) for the table of calls that were replaced.
