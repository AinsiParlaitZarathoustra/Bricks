# Background Tasks

Bricks keeps long work running without holding the conversation. A shell command can be started in the background with `Bash` (`background: true`), or a foreground command that is still running after its wait is handed over as a background job. The model follows these jobs with `Job`. Delegated work runs in parallel sub-agents, and each one can work in its own git worktree.

---

## Background Commands

### Starting a Command

`Bash` returns one of two ways when a command is still running:

* **At once**, with `background: true`. The call returns as soon as the job has started, with its `job_id` (`job_` and 12 hexadecimal characters), its pid, its state, its readiness and its working directory.
* **After `yield_time_ms`**, for a foreground command still running. The call returns with status `Running`, the same `job_id`, pid, state and working directory, and the stdout and stderr cursors. The command is not restarted and not killed, and its `timeout` still applies.

### States and Readiness

* **States**: `running`, `completed` (exit 0), `failed` (a non-zero exit, or a signal Bricks did not send) and `stopped`. The exit code exists only after a normal exit.
* **Running is not ready.** With `ready_pattern`, readiness is reported when a line matches. Without it, the result says readiness was not checked.
* **Ready is not proof.** Readiness does not show that a service works. Check it with a request of its own.

### Tools

#### Job

The calling agent's jobs, with one action per call. `action` defaults to `list`. Every other action needs the `job_id` that `Bash` returned.

| action | effect |
|---|---|
| `list` | your jobs: state, exit code or signal, pid, duration, readiness, lines and bytes per stream, working directory, command |
| `status` | the same line, then the raw log paths: live while the job runs, durable copies once kept |
| `output` | `stdout` or `stderr`, from line `offset` (0-based) for `limit` lines (200 by default, 2000 at most), or the last `limit` lines with `tail`. A header gives the range, the totals, what is no longer in memory and the next offset. Output is bounded in bytes: a line longer than the page is cut and marked |
| `wait` | until the job ends or `timeout_ms` (60000 by default, 600000 at most). A timeout stops nothing |
| `stop` | TERM to the process group and its tree, a grace period (2 s), then KILL. Idempotent: a job that already ended is a success |

Unknown fields and out-of-range values are refused, not corrected. A job that is not yours, or an unknown id, gets `No accessible job with this id`: the same answer in both cases.

**Permission:** Execute for `stop`; ReadOnly for `list`, `status`, `output` and `wait`.

The full input and output of each action are in `docs/shell.md` in the repository, section 3.

### Example

```
Bash { command: "npm run dev", background: true, ready_pattern: "ready in \\d+", ready_timeout: 30000 }
   → Started job job_… (pid …); state running; readiness is reported when a line matches

Job { action: "output", job_id: "job_…", stream: "stdout", offset: 0, limit: 50 }
   → the first lines of output, and the next offset to read on from

Bash { command: "curl -fsS http://localhost:3000/health" }
   → checks the service itself: readiness alone is not proof

Job { action: "stop", job_id: "job_…" }
```

### Limits and Lifetime

* **Quota.** `[background] max_jobs` (default 16) counts the running jobs of the session and the places being started. A place is reserved before anything starts. Beyond the limit, the start is refused with nothing launched: there is no queue.
* **Ownership.** A job is visible and stoppable only to the agent that started it. A frontend sees every job of its session.
* **Lifetime.** A background job survives the turn that started it and ends with the session. A yielded command is not durable: it ends with the run that started it. A sub-agent's jobs stop when it ends, and no job outlives Bricks.
* **Bounded capture.** Per stream, 5 000 lines and 1 MiB (`[background] output_buffer_bytes`) are kept in memory; a line longer than 64 KiB is cut and marked. Raw logs are kept up to 50 MiB per stream in the session's directory, and copied there when the job ends.
* **Events.** `job_started`, `job_output` (throttled counts, never the text) and `job_finished`.
* **Without a job registry.** `bricks_tools::shell()` has no registry: a command that may become a job is refused before it starts. See [Built-in Tools](/docs/built-in-tools) for the sets.

<Callout>
Prefer `background: true`, or a yield, to `cmd &` inside a foreground command. The leftovers of `cmd &` are stopped when that command ends.
</Callout>

## Sub-agents

`Agent` and `Agents` start sub-agents, which always run in parallel: the call returns their ids at once. `AgentControl` gives their results (`wait`, then `result`), and each sub-agent works in its own git worktree by default (`isolation: auto`). Its changes come back as a ChangeSet, which `AgentControl` inspects, applies (`apply_changes`) or discards (`discard_changes`); nothing reaches the working directory before that. The tools are listed in [Built-in Tools](/docs/built-in-tools#sub-agent-tools). Their limits and isolation rules are in `docs/agents.md` in the repository.

To work on another branch by hand, use `Bash` with `git worktree add -b {branch} {path}` and, when done, `git worktree remove {path}` (without `--force`: git refuses a worktree with uncommitted changes).
