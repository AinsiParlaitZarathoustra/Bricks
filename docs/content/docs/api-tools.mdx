# bricks-tools

Tool execution system with built-in tools, a granular permission model, a bash command safety analysis (SDK primitive), and Agent Skills (`SKILL.md`) served by `bricks-skills`.

---

## Tool Trait

Every tool implements this trait. The `#[derive(Tool)]` macro generates the boilerplate for tools that implement `ToolExecute` (see [Custom Tools](#custom-tools)).

```rust
#[async_trait]
pub trait Tool: Send + Sync {
    /// Tool name (used by the model to invoke it)
    fn name(&self) -> &str;

    /// Human-readable description shown to the model
    fn description(&self) -> &str;

    /// JSON Schema for the input parameters
    fn input_schema(&self) -> Value;

    /// Permission level required
    fn permission_level(&self) -> PermissionLevel { PermissionLevel::None }

    /// Permission level for this specific input (default: permission_level())
    fn permission_level_for(&self, _input: &Value) -> PermissionLevel { self.permission_level() }

    /// Category for grouping
    fn category(&self) -> ToolCategory { ToolCategory::Custom }

    /// The job registry this tool records or reads jobs in (`Bash`, `Job`)
    fn job_registry(&self) -> Option<Arc<JobRegistry>> { None }

    /// The same tool on `registry`, for a tool that works with jobs
    fn on_job_registry(&self, registry: &Arc<JobRegistry>) -> Option<Box<dyn Tool>> { None }

    /// Execute with JSON input and context
    async fn execute(&self, input: Value, ctx: &ToolContext) -> ToolResult;
}
```

### ToolResult

```rust
ToolResult::success("File contents here");
ToolResult::error("Permission denied");
ToolResult::success("data").with_metadata(json!({"size": 1024}));
```

| Method | Description |
|--------|-------------|
| `ToolResult::success(content)` | Successful execution. Content is returned to the model. |
| `ToolResult::error(content)` | Execution failed. The model sees the error and can retry or adapt. |
| `.with_metadata(value)` | Attach structured metadata (not shown to model, available in events). |
| `.with_images(images)` | Show images to the model with the result: `Vec<ToolImage>` (`bricks::tools::ToolImage`: `media_type`, `data_base64`, `path`, `bytes`). How they reach the model depends on the model; see [Multimodal Input](/docs/multimodal#images-returned-by-tools). |

## Custom Tools

### With Derive Macro

The fastest way to create a tool. The macro generates `Tool` impl, JSON schema, and input deserialization from your `ToolExecute` implementation.

```rust
use bricks::prelude::*;
use schemars::JsonSchema;   // the prelude exports the crates, not the derive names
use serde::Deserialize;

#[derive(Tool)]
#[tool(name = "search", description = "Search the documentation", permission = "read_only")]
struct SearchTool;

#[async_trait]
impl ToolExecute for SearchTool {
    type Input = SearchInput;

    async fn run(&self, input: SearchInput, ctx: &ToolContext) -> ToolResult {
        // Your implementation
        let results = do_search(&input.query, input.limit);
        ToolResult::success(format!("Found {} results for '{}'", results.len(), input.query))
    }
}

#[derive(Deserialize, JsonSchema)]
struct SearchInput {
    /// The search query
    query: String,

    /// Maximum number of results to return
    #[serde(default = "default_limit")]
    limit: usize,
}

fn default_limit() -> usize { 10 }

// Stub for the example: your search goes here.
fn do_search(_query: &str, _limit: usize) -> Vec<String> { Vec::new() }
```

**Derive attributes:**

| Attribute | Values | Description |
|-----------|--------|-------------|
| `name` | any string | Tool name the model uses to invoke it |
| `description` | any string | Shown to the model in the tool list |
| `permission` | `none`, `read_only`, `write`, `execute`, `dangerous` | Required permission level |

The `Input` type must derive `Deserialize` (serde) and `JsonSchema` (schemars). Field doc comments become parameter descriptions in the schema. An input field the tool does not declare is an error, with a message that suggests the correct name.

The expansion names the types it uses by their full paths under `bricks_tools` (`bricks_tools::PermissionLevel`, `bricks_tools::ToolCategory`, …). A crate that uses `#[derive(Tool)]` therefore declares `bricks-tools` as a dependency next to `bricks`, as it had to declare `cersei-tools` before the rename. See [Migration](/docs/migration).

### Manual Implementation

For full control, implement `Tool` directly:

```rust
use bricks::prelude::*;
use serde_json::Value;

struct ManualTool;

#[async_trait]
impl Tool for ManualTool {
    fn name(&self) -> &str { "manual_tool" }
    fn description(&self) -> &str { "A manually implemented tool" }

    fn input_schema(&self) -> Value {
        serde_json::json!({
            "type": "object",
            "properties": {
                "input": {
                    "type": "string",
                    "description": "The input value"
                }
            },
            "required": ["input"]
        })
    }

    fn permission_level(&self) -> PermissionLevel {
        PermissionLevel::ReadOnly
    }

    async fn execute(&self, input: Value, _ctx: &ToolContext) -> ToolResult {
        let text = input["input"].as_str().unwrap_or("");
        ToolResult::success(format!("Processed: {text}"))
    }
}
```

```rust
let agent = Agent::builder()

    .tool(SearchTool)                // + your custom tool
    .tool(ManualTool)                // + another

```

## Permission Levels

Every tool declares a permission level. The level gives the call its class of action (read, write, execute or network), and the session's permission policy decides the call before it runs. See [Permissions](#permissions-the-engine-and-the-approver) below, and `docs/cli.md#permissions` in the repository for the frontends.

### Permissions: the engine and the approver

Each agent decides its calls with one engine (`bricks_agent::permission`).
The engine reads the session's **policy**, a `SessionPolicy` with a profile
and, for CUSTOM, its rules. The calls it says to ask about go to the
**approver**, a `PermissionPolicy` that answers for one call only.

| Profile | Read | Write | Execute | Network (web tools) |
|---------|------|-------|---------|---------------------|
| `PermissionProfile::Ask` | allowed | asked | asked | asked |
| `PermissionProfile::Execute` | allowed | allowed | allowed | allowed |
| `PermissionProfile::Custom` | the effect of its class, or of its tool | the same | the same | the same |

A tool's own CUSTOM rule wins over its class. `Forbidden` tools are refused
in every profile. A policy never chosen behaves as ASK.

| Approver | Answer to a call the policy asks about |
|----------|-----------------------------------------|
| `AllowAll` | Allows the call. |
| `DenyAll` | Refuses the call, with a reason. |
| `InteractivePolicy::new(handler)` | Calls `handler(&PermissionRequest)`, which returns a `PermissionDecision`. |
| `InteractivePolicy::via_stream()` | Waits for `respond_permission` on the event stream. |

`PermissionDecision` is `Allow`, `Deny(reason)` or `AllowOnce`. The engine
turns an allow into a decision for that call only: nothing is granted for
later calls. A call decided under a policy stays decided by it when the
policy changes meanwhile; calls decided afterwards follow the new revision
(`PermissionVerdict::policy_revision`).

The builder chooses the profile and the approver:

- `.permission_policy(approver)` sets the approver. Alone, it gives the ASK profile.
- `.permission_profile(SessionPolicy)` sets the policy. Without it, an agent with an approver is ASK, and one without an approver is EXECUTE.
- `.permission_cell(cell)` shares one policy with other agents of the same session, so a change reaches them at their next call. Sub-agents use `.permission_engine_arc(..)` with their parent's engine.

```rust
use bricks::prelude::*;

// ASK with an approver that refuses: reads run, writes, commands and web calls are refused.
let read_only = Agent::builder()
    .provider(bricks::provider_from_config(None, "my-provider/my-model")?)
    .tools(bricks::tools::coding())
    .permission_policy(DenyAll)
    .build()?;

// EXECUTE: everything runs, nothing is asked.
let open = Agent::builder()
    .provider(bricks::provider_from_config(None, "my-provider/my-model")?)
    .tools(bricks::tools::coding())
    .permission_profile(SessionPolicy::chosen(PermissionProfile::Execute))
    .build()?;

// CUSTOM: no shell or sub-agent, writes asked, the web tools allowed.
let mut policy = SessionPolicy::chosen(PermissionProfile::Custom);
policy.custom.execute = PermissionEffect::Deny;
policy.custom.write = PermissionEffect::Ask;
policy.custom.tools.insert("WebFetch".into(), PermissionEffect::Allow);
let custom = Agent::builder()
    .provider(bricks::provider_from_config(None, "my-provider/my-model")?)
    .tools(bricks::tools::coding())
    .permission_profile(policy)
    .permission_policy(DenyAll) // answers the calls that are asked
    .build()?;
```

`SessionPolicy` is plain data (serde). The library stores nothing by itself:
`bricks_agent::permission::PermissionStore` keeps the default for new sessions
in `permissions.json`, and each frontend keeps every session's policy with the
session.

## Bash Safety Analysis

`BashTool` always asks the `PermissionPolicy` at the `Execute` level; nothing
classifies the command before it runs, and the approval does not depend on
the command text.

`bricks_tools::tool_primitives::bash_safety::analyze_command` is a separate
primitive: it parses a command with tree-sitter and reports a risk level
(`BashRiskLevel`: `Safe`, `Moderate`, `High`, `Forbidden`), the commands seen and the paths
written. A caller may use it, for example to show a warning; it is not wired
into the tool's permissions. See
[Code intelligence](/docs/code-intelligence#bash-command-safety-analysis).

The heuristic `bricks_tools::bash_classifier` module (`classify_bash_command`,
its `BashRiskLevel` with `Low`/`Medium`/`Critical`) was removed in 0.5.0;
use `bash_safety` instead.

## Skills

Skills are [Agent Skills](https://agentskills.io/specification) (`SKILL.md`), served by the `bricks-skills` crate (`bricks::skills`). Give an agent a skills service and the `Skill` tool is registered, the catalog goes into its system prompt, and its activations are its own:

```rust
use std::sync::Arc;
use bricks::skills::{SkillAccess, SkillsService};

let service = Arc::new(SkillsService::standard(project_dir, Some(store_dir)));   // project: &Path, store: Option<&Path>
let access = SkillAccess::new(service);
let agent = Agent::builder()
    .provider(provider)
    .tools(bricks::tools::coding())
    .skills(access)
    .build()?;
```

Sources: the store (`<bricks_home>/skills/<name>/`, where the person's installed skills live) and the built-in `create-skills`. No folder of the project or of the home directory is read: `~/.claude/skills`, `~/.agents/skills`, `<project>/.claude/skills` and `<project>/.agents/skills` are never read, copied or modified. An embedder adds its own folders explicitly, with `SkillRoot::explicit` in `SkillsSetup::extra_roots`; `bricks_skills::standard_roots` is an opt-in helper. A project folder reaches the model only when it is an explicit source and a trust decision was taken for the session. `.claude/commands/*.md` and `$ARGUMENTS` templates are not read. See `docs/skills.md` in the repository.

## Persistent Shell

`BashTool` runs each call as its own `bash` process, started from the agent session's state. Commands of one session run side by side. When a command ends normally, its working directory, exported variables, functions and aliases are published to the session (the most recently launched command wins per field); a command that is interrupted, times out or calls `exec` publishes nothing, and the result says so. Non-exported variables and shell options do not persist. `PowerShellTool` keeps one interpreter per agent session, unchanged. Stdin is empty unless an `input` is given, and no command has a controlling terminal. See `docs/shell.md` §1.

```rust
// First call: cd /tmp
// Second call: pwd → /tmp (the working directory persists)
// Third call: export FOO=bar
// Fourth call: echo $FOO → bar (variables persist)
```

Closing the agent (`agent.close().await`, async) or dropping it stops the session's processes. Dropping does it synchronously and forced (`crates/bricks-agent/src/lib.rs:515-518`).

## Background Jobs

A job is a command that keeps running after its call returned: one started with `background: true`, or one handed over after `yield_time_ms`. The jobs of a session are kept by a `JobRegistry` (`bricks_tools::jobs`), which holds the quota, the owner of each job, its events and its logs. `JobSettings` (the `[background]` table) sets the limits, with these defaults: `max_jobs` 16, `output_buffer_bytes` 1 MiB per stream, `max_line_bytes` 64 KiB, `raw_log_bytes` 50 MiB per log, `stop_grace_ms` 2000, `max_page_bytes` 64 KiB.

| Function | Tools |
|---|---|
| `shell()` | `BashTool::default()` (no registry: a command that may become a job is refused before it starts), `PowerShellTool` |
| `shell_with_jobs(registry)` | `BashTool` and `JobTool` on `registry`, `PowerShellTool` |
| `coding()`, `all()` | `shell_with_jobs` on a fresh registry |
| `on_job_registry(tools, &registry)` | Each tool whose `job_registry()` is set moves to `registry` (`on_job_registry()`); `JobTool` is added when Bash is present without it |

```rust
use std::sync::Arc;

let registry = bricks_tools::jobs::JobRegistry::new(Default::default(), None);
let tools = bricks_tools::shell_with_jobs(Arc::clone(&registry));
```

When an agent is built, `AgentBuilder::build` looks at its job tools. If its extensions hold a `JobsHandle` (sessions and sub-agents get one), the tools are put on that registry. Otherwise the registry of the tools becomes the agent's `JobsHandle`. Tools on two different registries are refused with `CerseiError::Config` before any model call.

A job belongs to the agent that started it: `JobTool` and `Bash` read the `JobOwner` in the tool context, which the runner sets for each agent. Without an owner, `Bash` refuses a command that may become a job, and `Job` answers with an error.

Code that reads a job's output uses `Task::read(stream, OutputPosition::Offset(n) | OutputPosition::Tail, limit)` (`bricks_tools::shell::background`). It returns a `Page`: its lines with their absolute line numbers, its totals, and `evicted`, the number of lines no longer in memory.
