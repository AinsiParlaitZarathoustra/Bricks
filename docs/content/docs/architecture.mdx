# Architecture

Bricks has two layers. The **engine** runs an agent: the loop, the providers,
the tools, the approvals, the context, the sessions. The **frontends** present
the engine: the `bricks` command, Bricks Desktop, and an application of your
own built with the library. The frontends keep no conversation store of their
own. The session store of the engine is the authority on the conversation, and
a frontend reads it again when a session is resumed.

```text
frontends    bricks-cli (the `bricks` command)      apps/bricks-desktop (Bricks Desktop)
             your application, through the `bricks` facade
                      │  commands ↓        ↑ events      (bricks_agent::control)
engine       bricks-agent: Controller → Agent (loop, approvals, context, sessions)
                      │
services     bricks-provider · bricks-tools · bricks-memory · bricks-compression
             bricks-semantic · bricks-web · bricks-mcp · bricks-skills · bricks-hooks
                      │
foundation   bricks-types (messages, errors, stream events, the shared HTTP client)
```

The engine never depends on a frontend. `bricks-config` assembles the engine
for the frontends: the Bricks home folder, the provider registry and the
project's `bricks.toml`. A library user builds an `Agent` with the builder and
calls the loaders it needs, such as `provider_from_config`.

## Principles

1. **Traits at the seams.** A provider, a tool, a memory backend, a permission
   policy and a hook are traits. Each one can be replaced by your own
   implementation.
2. **Configuration for models, code for behaviour.** Models, limits, prices and
   reasoning profiles come from `providers.toml`. Project settings come from
   `bricks.toml`. Nothing is built in: a model is never chosen silently, and no
   model catalogue is compiled into the engine.
3. **One contract for every frontend.** The `bricks_agent::control` module takes
   typed commands and emits versioned events. The `bricks` command and Bricks
   Desktop use the same contract, so both present the same events and accept the same commands.
   The JSONL schema is documented in `docs/cli.md` in the repository.
4. **Permissions belong to the engine.** Each session's policy (ASK, EXECUTE or
   CUSTOM) is applied by the engine for every frontend. A frontend only shows
   the calls the engine asks about and answers for one call.
5. **Few subprocesses.** File, search and web tools run in the process. A
   subprocess starts for a command the agent runs (`Bash`, `PowerShell`, a
   background job), and for a language server when one is configured.

## What the ADK provides, and what a session is given

The ADK has a built-in tool set, `bricks_tools::all()`, with file, shell,
web and planning tools. The `bricks` command and Bricks Desktop give a session
its own set: the coding tools, the plan, the skill tool when skills are
enabled, and the sub-agent tools when `[agents]` is enabled.
The list is in the *Tools of a session* section of `docs/cli.md` in the
repository. An agent you build with the library chooses its own tools.

## Sub-agents

When `[agents] enabled` is true, which is the default in a session, the agent
can start sub-agents with the native tools `Agent`, `Agents`, `AgentControl`
and `AgentProfiles`.

* A sub-agent runs its own loop with a fresh context. It gets its parent's
  permissions and at most its parent's tools.
* `Agents` runs several independent tasks at the same time. Each parallel
  writer works in its own git worktree, and its changes come back as a
  ChangeSet that is inspected and applied separately.
* A sub-agent is cancelled with the run that started it.
